# Renpet offline storage and calendar exchange

Renpet stores appointments, calendars, preferences and reminder state exclusively
in the device's IndexedDB. There are no user accounts, analytics, synchronization
servers, or remote APIs for personal information.

## Storage and backups

- Appointments, calendars and preferences use a single IndexedDB database.
- Writes complete only after an IndexedDB transaction commits.
- Manual JSON backup contains the current Renpet scheduler and preferences.
- Restore validates the file and updates both records atomically.
- There is no migration from old localStorage records or older backup schemas.
- Browser data deletion and storage eviction are still possible. Manual exports
  are therefore important even when persistent storage is granted.

## ICS exchange

ICS exchange is an optional bridge with standard calendar applications. Its
Gregorian serialization is not Renpet's internal recurrence system. The native
Egyptian daily and 10-day intervals are exported as standard calendar rules;
Egyptian monthly/yearly recurrences are expanded over a defined ten-year
export horizon. Unsupported external recurrence and time-zone definitions
are rejected by the importer rather than inferred.

## Reminders and offline operation

Reminders are optional and disabled by default. Their schedules and delivered
identifiers remain in the local database. Foreground reminders may use
notifications when permitted or in-app alerts. Reliable notifications after
the PWA is fully closed are not supported without a push server, which Renpet
does not use.

A release build creates one service worker and caches the application shell,
date engine, fonts, keyboards, festival catalogs and seasonal artwork locally.
The service worker is generated by `tools/build_service_worker.py` and is not
maintained as independent source. The initial installation and static app
updates need connectivity; personal calendar records never do.
